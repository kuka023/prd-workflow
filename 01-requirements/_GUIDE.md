# 需求边界与模板裁剪

规则以 [constitution.md](../constitution.md) 为准。业务闭环 PRD 与独立能力规格共用 `_TEMPLATE-module-prd.md`，按本文选择边界，再按模板裁剪。

## 1. 默认按业务结果划分

默认使用 `spec_kind: business`。一份 PRD 围绕一个主要业务目标，写清起点、完成条件、失败处置和验收负责人。可以依赖明确的上游契约，不要求每份都从数据进入写到最终使用（CN-46）。模块目录只负责归档，取值见 `00-context/modules.md`。

以下仅为边界示例，不对应任何项目已确认的范围或需求 ID：

| 业务目标 | 起点与完成条件示例 | 内部能力示例 |
|---|---|---|
| 资料提交 | 提交资料，直到资料可供使用，或失败原因明确且可处置 | 录入、校验、审核、处理状态 |
| 资料维护 | 发起资料变更，直到变更按约定影响后续使用 | 编辑、版本、发布或下架 |
| 查询使用 | 在已有可用资料的前提下查询，直到得到符合要求的结果或明确的无结果说明 | 查询、筛选、排序、结果展示 |

跨目标的「提交后能够查到」可以由一份指定的业务 PRD 承担集成验收，引用相关需求的 AC-n / M-n，不在每份 PRD 重写整条路径。启用领域包时，该领域的边界示例见领域包的 `boundary-examples.md`。

## 2. 何时拆出独立能力规格

存在以下实际需要时，可使用 `spec_kind: capability`（CN-52）：跨闭环复用、独立责任团队，或独立评测与发布。文档较长、涉及模型效果，本身不是拆分理由。

能力规格仍放在 `01-requirements/<模块>/<需求ID>-*.md`，沿用稳定 ID、素材包、生成、审稿与 lint 流程。已有组件空壳不自动转换；边界与拆分理由须由需求负责人确认，缺依据时登记提案与 Q-n。

| 内容 | 业务闭环 PRD | 独立能力规格 |
|---|---|---|
| 本文责任 | 业务结果与最终验收 | 输入到输出的能力承诺与约束 |
| 确定性验收 | 业务操作、状态、权限、异常 | 输入输出、元数据传递、异常及约定行为 |
| 效果验收 | 适用的业务级效果 | 适用的局部能力效果 |
| 关联方式 | 引用能力规格的条目与契约；实际前置能力列入 depends_on | business_requirements 列出承担业务验收的 PRD；正文引用负责人和 AC-n / M-n |

`business_requirements` 只表达验收归属，不要求业务 PRD 先完成才能开发能力，也不生成反向依赖。业务 PRD 依赖能力时仍按 `depends_on` / `blocks` 声明；能力不得仅因被业务 PRD 引用而反向依赖该 PRD。

拆出后，业务 PRD 不复制能力内部规格，但保留端到端场景、业务效果目标、集成失败处置与验收责任。局部指标通过不能替代业务验收（CN-47）。契约与指标定义仍引用 `02-contracts/`、`03-quality/`。

## 3. 功能与效果分别判断，共同验收

两种规格均保留功能验收。只要本文承诺涉及模型质量，就保留效果验收；不得根据 module、旧 type 字段或是否有界面机械判断。

- 业务场景即使依赖独立的模型能力（如自动分类），仍需验收最终业务结果的效果。
- 独立的模型能力除了自身的效果评测，也须验收约定的输入输出边界、权限元数据和失败行为。
- 纯配置能力可以只做功能验收；若本期同时承诺配置后的效果，则还需效果验收。

效果章节按适用性覆盖任务边界、评测协议、输入形态、基线与门槛、Bad Case、运行观测；延迟、成本、更新与重建、策略对比等有实际需求时展开。业务参数须有来源，不从模板示例推导为事实；具体门槛写在验收方案中，需求只引用（CN-57）；算法选型仍归实现方或 ADR。

## 4. 当期批次与历史文件

只展开 frontmatter `batch` 的范围（CN-49）。业务 PRD 须完成当期闭环，能力规格须完成当期输入输出承诺；不足时提出批次调整建议。

现有需求 ID、模块和内容保留。下次按新规范生成或修订时，明确 `spec_kind`、能力规格的业务验收归属及实际依赖，再更新 `template_version`；不得仅为消除版本提示而修改版本号。新增、合并或废弃具体需求的映射由需求负责人确认。
