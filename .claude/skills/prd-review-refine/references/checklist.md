# 审稿清单

14 类问题。「默认严重度」为通常情况，具体以 constitution CN-41 为准。「lint」列表示 `prd_lint` 已覆盖其中可机械判定的部分，审稿只需判断剩余部分。

| # | 类别 | 默认严重度 | lint |
|---|---|---|---|
| C-1 | 伪需求与问题定义偏差 | P0 | — |
| C-2 | 范围泄漏 | P1 | — |
| C-3 | 不可测试的描述 | P1 | CV02 |
| C-4 | 缺失的异常与权限边界 | P1 | PM01、RF04 |
| C-5 | 重复或冲突的契约 | P1 | — |
| C-6 | 没有证据的数字 | P0 | SR01 |
| C-7 | 编造的业务规则 | P0 | SR01–SR03 |
| C-8 | 产品决策与技术实现混杂 | P1 | WR01 |
| C-9 | AC 覆盖缺口 | P2 | CV01、CV03 |
| C-10 | 设计结论不完整 | P2 | — |
| C-11 | 冷读不可理解 | P2 | — |

## C-1 伪需求与问题定义偏差

**判据**：问题陈述描述的其实是解决方案（「需要一个 X 功能」）；找不到谁受影响、证据、不做的后果；本期范围解决的不是问题陈述中的问题。

- 反例：「P-1 需要支持批量上传」——这是方案。
- 正例：「P-1 运营官每周手工逐个上传约 N 份文档，耗时约 M 小时（来源：SRC-2）」。

## C-2 范围泄漏

**判据**：功能条目、规则或 AC 无法对应到任何 `S-n`；正文实现了 `O-n` 中列为不做的内容；「顺便」「同时支持」引入的能力没有来源；`S-n` 按技术层而非纵向切片划分。

## C-3 不可测试的描述

**判据**：出现「快速」「友好」「合理」「及时」「尽量」等无法判定的词；Then 不可观测（「系统正确处理」）；验证层级填了，但在该层级无法观察到 Then 描述的结果。

涉及效果时，核对任务范围、评测集版本、判分协议与评审方式是否明确，业务效果与局部效果是否分别验收。仅有准确率门槛而没有评测协议属于不可测试；协议与指标口径须引用质量真源，门槛只以验收方案条目引用（CN-57），核对所引方案的适用范围是否覆盖本需求或其发布批次。

- 反例：Then「系统提示用户」。
- 正例：Then「页面显示错误信息『名称已存在』，名称输入框保留用户输入」。

## C-4 缺失的异常与权限边界

**判据**：主路径中的每个外部调用、用户输入、状态变更是否都有对应的 `EX-n`；每个 `EX-n` 是否给出用户下一步；权限矩阵是否覆盖第 8 章出现的全部操作；涉及数据可见范围限制的，是否写明过滤发生在哪一层。

能力规格还须检查输入输出约束及元数据契约的引用；效果故障后的继续、停止、拒答或人工处置是否有依据，是否默认跳过了不可跳过的红线检查；运行观测与效果变化处置是否有责任方。

## C-5 重复或冲突的契约

**判据**：需求中出现字段定义表（字段、类型、长度），而不是引用 `02-contracts/`；与 `02-contracts/` 的定义冲突；与其他需求的规则冲突（同一判定在两份需求中结论不同）。

## C-6 没有证据的数字

**判据**：阈值、时限、数量、比例没有来源，或来源中不含该数字。整数、整百、整十的「合理值」尤其可疑。

## C-7 编造的业务规则

**判据**：来源标注存在，但素材原文不支撑；把行业惯例当作客户确认的规则；把素材中一方的主张写成已确认的结论；在已溯源的事实上增加了限定词（「只」「必须」「全部」）或新条件（CN-43）。

**定级**：业务规则、权限、范围、数字、设计结论无依据为 P0；提示文案、界面措辞等表达层细节无依据为 P2。

## C-8 产品决策与技术实现混杂

**判据**：出现技术选型（数据库、框架、模型名称）、代码路径、接口实现细节、算法步骤。产品需求只写「应达到什么」，不写「用什么实现」。确需记录的技术约束写入 ADR 并引用。

## C-9 AC 覆盖缺口

**判据**：lint 已算出未覆盖项；审稿判断其余情况：AC 虽然覆盖了某条规则，但只验证了正向情形，没有验证边界或反面情形。

## C-10 设计结论不完整

**判据**：缺少被否决的备选方案；缺少「接受的代价」或「复议条件」；结论与第 3 章范围矛盾。

## C-11 冷读不可理解

**判据**：见 SKILL.md 第 2 步。凡是实现方需要自行做产品决定才能继续的地方，定为 P1。

## C-12 违反 constitution

**判据**：任何 `CN-n` 被违反，问题描述中注明违反的编号。违反第 1、3、6 节为 P0；其余按实际影响定为 P1–P3（CN-42），例如来源标注写法不规范为 P3。

## C-13 表达与信息密度

**判据**：冗余重复、空话套话、口语化或情绪化表达（CN-38）、代词、禁用同义词、残留的模板写作说明。

## C-14 责任边界或业务验收归属不完整

**判据**：2.1 的环节在第 8 章没有对应的功能条目，或某个环节没有任何 AC；缺少贯穿全程的端到端验收；当期批次缺少某个环节，闭环无法闭合，却没有提出批次调整建议（CN-49）；2.4 列出的接口与对方闭环的描述不一致，或未在 frontmatter 声明依赖。

按 spec_kind 区分边界：business 可以从已满足的上游契约开始，不强制扩展到所有业务路径；capability 验证输入到输出，检查拆分理由是否成立及是否已经确认。能力规格须关联最终业务 PRD、负责人及有效 AC-n / M-n；关联应与 business_requirements 一致。业务 PRD 不得因能力已拆出而删除业务效果验收。验收归属不构成反向开发依赖；跨需求路径须有明确的集成验收承接方。

- 反例：当期批次有「下架」，但「清除缓存」排在后续批次，PRD 未提出任何问题。
- 正例：同样情况下，开放问题提出「将清除缓存提前到当期批次」，并写明阻塞什么。
