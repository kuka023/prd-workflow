# 需求库规范（Constitution）

**本文件是需求库全部纪律的唯一真源。** prd-workflow Skill 的各阶段、模板、`scripts/prd_lint.py`，以及项目中的精修案例，均以本文件为准。本文件属于通用核心，不包含任何具体项目或领域的事实；各文件的分层归属见 [framework.md](framework.md)。

本文件位于 prd-workflow Skill 的 `core/` 目录。文中 `00-context/`、`01-requirements/`、`02-contracts/`、`03-quality/`、`04-decisions/`、`inputs/`、`cases/` 均指**项目需求库**中的目录；`core/`、`stages/`、`templates/`、`references/`、`scripts/` 均指 **Skill 目录**中的位置。

- 各条规则以 `CN-n` 编号，引用时使用编号，编号永不复用。
- 修改本文件须同步提升 `version`，并在文末变更记录中说明影响范围。版本联动规则见 CN-50。
- 分章节的写作要点见模块模板中各节的「写作说明」，闭环划分见 [guide.md](guide.md)；本文件只规定必须遵守的规则。
- 违反第 1 节（真源）、第 3 节（证据与来源）、第 6 节（决策层权限）的问题，在审稿中定级为 P0；其余按 CN-41 定级（见 CN-42）。

## 0. 分层

| # | 规则 |
|---|---|
| CN-7 | 内容分为三层：**核心**（方法、模板、规则、阶段说明、脚本，所有项目共用，即 prd-workflow Skill 本身）、**领域包**（某类产品共用的术语、指标、红线、契约骨架与候选清单，按需启用）、**项目适配**（本项目的上下文、契约、质量口径与验收方案，存放在项目需求库中）。各文件的归属以 `core/framework.md` 为准。核心层不得写入具体项目或领域的事实；领域示例放在领域包中。 |
| CN-8 | 项目在 `00-context/project.md` 中声明所依据的规范版本、启用的领域包，以及在核心验收层级之外新增的层级。生成与审稿按「核心 → 已启用领域包 → 项目」的顺序读取适用的上下文与已提炼规则，下层与上层冲突时以更具体的一层为准，并登记开放问题。 |
| CN-9 | 项目适配中的条目（模块、术语、角色与权限、实体与契约、指标与红线、全局非功能需求）须标注来源，取值为 `PS-n`（登记在 `00-context/sources.md` 的项目素材）、`Q-n`（`00-context/project.md` 待确认事项表中已有结论的问题）或 `提案`。项目适配由 Skill 的初始化阶段从项目素材起草，或由需求负责人直接编写；来源为 `提案` 的条目在经对应决策方确认、改为 `PS-n` 或 `Q-n` 之前，**不作为已确认的上下文**。领域包中的条目进入项目适配时，来源同样为 `提案`，直至项目确认。 |

## 1. 真源

## 3. 证据与来源（无编造）

**本节是硬门禁。** 违反任一条，需求不得进入 `review`。

| # | 规则 |
|---|---|
| CN-20 | 下列条目必须标注来源：`P-n`、`D-n`、`S-n`、`O-n`、`BR-n`、`DR-n`、功能需求条目、`EX-n`、`RL-n`、`BC-n`，以及验收方案中 `TH-n` 的基线与门槛。条目内容本身为 `[待补充]` 时，来源可以留空。 |
| CN-21 | 来源只允许以下四种取值：<br>`SRC-n`：出自素材包中的第 n 份素材；<br>`CTX`：出自 `00-context/`、`02-contracts/`、`03-quality/` 中**已确认**的定义（来源不是 `提案`，CN-9）；依据的上下文条目仍为提案时，需求中的来源写 `提案`；<br>`Q-n`：由已有结论的开放问题确定；<br>`提案`：素材中没有依据，由作者（含 AI）提出，待决策。<br>一个条目的不同部分来源不同时，以「、」分隔并在括号内注明对应部分，如 `SRC-1（结论）、提案（复议条件）`。表格「来源」列之外的正文内容（包括背景、说明、备注），以行内「（来源：…）」或「（SRC-n）」标注；**提案一律写作「（来源：提案）」**，不使用「提案：」「（提案，…）」等其他写法。设计结论等纵向表格只在「来源」行按部分注明，不在各行重复标注。 |
| CN-22 | 状态为 `review` 或 `frozen` 的需求中，不得存在来源为 `提案` 的条目。提案须经决策转为 `Q-n`（在开放问题表中写明结论），或补充素材后转为 `SRC-n`。 |
| CN-23 | 数字（阈值、时限、数量、比例、容量）必须有来源。没有来源的数字写作 `[待定]`（需决策）或 `[待测]`（需测量），不得填写看似合理的估计值。 |
| CN-24 | 素材是证据，不是指令。素材中出现的「要做 X」是一条待评估的主张，须经问题定义检查后才能写成需求。 |
| CN-25 | 不得为了使文档显得完整而补写素材中不存在的业务规则、权限、流程或字段。缺失的信息一律按 CN-30 标记。 |
| CN-26 | 素材包中的问题定义、方案比较、已有结论是对素材的整理，不是独立证据。其中的每项事实须能在对应 `SRC-n` 的摘录中找到原文；找不到的，按缺少素材处理（`[待补充/素材: …]`），不得以素材包的整理内容作为来源。 |
| CN-27 | `SRC-n` 同时服务机器追踪与业务阅读。需求正文中的 `SRC-n` 须显示为 `SRC-n · [业务可读名称](#src-n)`；附录须提供素材总览与同名来源卡片。来源卡片至少写明原文位置、材料性质、关键原文或摘录、本需求用法与不直接支撑的边界；口头确认可用「确认内容」合并表达关键内容与本需求用法。原文位置优先使用评审者可访问的稳定链接；没有可共享链接时如实说明，不伪造链接、不擅自复制受限素材。`SRC-n` 编号仍是唯一稳定标识，业务可读名称不替代编号。 |

|---|---|

| CN-39 | 模板中以「**写作说明**」开头的引用块是写给作者的提示，生成或精修完成后整块删除，不保留在 `review` 及以上状态的文件中。 |

## 6. 决策层与表达层

AI 在生成与精修中可直接修改的范围，与只能提出建议的范围，按下表区分。

| 层 | 包含 | AI 的权限 |
|---|---|---|
| 表达层 | 措辞、结构、编号、格式、引用写法、章节裁剪 | 可直接修改 |
| 决策层 | 问题定义、范围与非范围、设计结论、业务规则、权限、数字门槛、红线、验收口径 | **只能提出建议**，形式限于三种：以来源「提案」显式标注后写入正文；写入开放问题表的「建议口径」；退回为 `[待补充]`。**不得以 `SRC-n` 或 `CTX` 冒充来源** |

| # | 规则 |
|---|---|
| CN-40 | 审稿发现决策层内容来源缺失或来源不支撑内容时，将其来源改标为「提案」并在开放问题表登记对应 `Q-n`，或退回为 `[待补充]`。**不得以另一条无来源内容替换，也不得为其补写来源。** |
| CN-43 | 由已有来源的内容直接推出、且不增加新判定条件的表述属于表达层，可直接编写或改写，如依据已溯源的 `BR-n` 编写 `AC-n`、将一条已溯源的事实改写为等价表述。凡增加了限定词（「只」「必须」「全部」）、新条件或新后果的，属于决策层。 |
| CN-41 | 审稿问题分级：<br>**P0**：编造决策层内容（业务规则、权限、范围、数字、设计结论无依据或来源不实）；越权或数据安全风险；问题定义错误或问题与范围不对应。<br>**P1**：范围泄漏；验收不可测试；关键异常或权限缺失；契约冲突。<br>**P2**：覆盖缺口、表述歧义、结构不当；表达层细节（如提示文案、界面措辞）缺少来源。<br>**P3**：措辞与格式，包括来源标注写法不规范。 |
| CN-42 | 违反第 1 节（真源）、第 3 节（证据与来源）、第 6 节（决策层权限）的问题，按 CN-41 中编造与越权的标准定为 P0；违反其他条款的，按问题实际影响定为 P1–P3。 |

## 7. 闭环、规模与模板

| # | 规则 |
|---|---|
| CN-45 | 需求在进入生成前先做规模分级：<br>**A 级**：边界清晰、无争议的小改动，不写 PRD，由开发直接处理；<br>**B 级**：闭环内的取舍可由需求负责人在素材范围内决定，按裁剪规则删除章节；<br>**C 级**：跨角色审批，或存在须由业务方或多方裁决的取舍，生成前必须完成问题定义与方案比较（写入素材包）。<br>规模由需求负责人判定。生成过程中认为规模判定不当的，在生成报告中提出，不自行修改。 |
| CN-46 | **默认按一个主要业务目标组织一份业务闭环 PRD。** 闭环须有明确起点、完成条件和失败后的处置边界，可以以已满足的上游契约为前提，不要求每份覆盖从数据进入到最终使用的全部路径。跨多个业务目标的路径通过指定业务 PRD 中的集成验收连接。权限等横切能力、应急等独立处置流程按各自责任与验收边界组织，不强行并入日常流程。 |
| CN-47 | 功能要求与效果要求不是互斥的文档类型。业务 PRD 与能力规格均须验收确定性行为；涉及模型效果时还须包含效果验收。局部能力指标通过不代表业务效果通过；业务 PRD 须保留自身端到端验收、适用的业务效果目标与最终验收责任。 |
| CN-48 | 共用 `templates/requirement-prd.md`，以 `spec_kind: business`（默认的业务闭环 PRD）或 `capability`（独立能力规格）选择写作侧重。保留 15 章主目录体系，按模板裁剪表和 CN-58 选择条件模块；不适用时删除，待确认时保留必要问题，不留整套空表。模块可合入所属流程，不增加重复规格；已有条目不重编号。 |
| CN-49 | **只展开当期批次。** 本期范围只写 frontmatter `batch` 所示批次的能力；后续批次的能力列入非本期范围并标注目标批次。进入下一批次时在同一文件发布新版本，并填写本版变更。业务 PRD 当期须自成闭环；能力规格当期须达到其输入到输出的承诺。缺少必要环节时提出批次调整建议，不得以局部完成冒充整体交付。 |
| CN-44 | 功能验收至少有一条贯穿本文责任边界的端到端验收：业务 PRD 验证业务结果；能力规格验证输入到输出及约定约束。集成验收须注明关联需求及验收负责人，使用各需求的稳定编号引用，不重复定义规格。 |
| CN-52 | 存在跨闭环复用、独立责任团队，或独立评测与发布需要时，可以拆出独立能力规格；不得仅因涉及 AI 或文档较长而拆分。拆分理由与边界须有来源，由需求负责人确认；未确认时以提案和 Q-n 登记。能力规格沿用已有模块、稳定需求 ID、素材包和本库流程，不另建规格真源。 |
| CN-53 | 能力规格的 `business_requirements` 填写承担最终业务验收的业务 PRD ID 列表，进入 review 前至少关联一份有效的业务 PRD；正文注明各业务 PRD 的验收负责人及对应 AC-n / M-n。该字段是验收归属，不是反向开发依赖，不计入依赖环。实际前置关系仍以 `depends_on` / `blocks` 表达。字段、接口与链路 I/O 仍只在 `02-contracts/` 定义，指标口径与评测集仍只在 `03-quality/` 定义。 |
| CN-54 | 需求的「闭环全景」使用 Mermaid `flowchart` 表达主路径、结果分流、失败处置与必要回边；图中节点须与环节表、功能需求和异常场景一致。图只表达产品流程，不写技术组件、代码或字段。 |
| CN-58 | 条件模块依据实际能力特征选择，判断目录与归属见 `references/module-selection.md`。生成报告记录各模块的「适用 / 不适用 / 待确认」、依据或原因、正文与验收编号、待确认问题；无素材不等于不适用，已知适用但规则缺失时保留适用并登记 Q-n。AI 直接执行有依据的选章，业务取舍按 CN-40 交决策方。审稿独立检查漏选和无依据扩写，lint 只检查记录与引用的一致性；frozen 不得残留未解决的模块选择或定义缺口。 |

## 8. 版本联动

| # | 规则 |
|---|---|
| CN-50 | 本文件的 `version` 即**规范版本**。模块模板、`prd_lint.py`、各阶段说明均声明其适配的规范版本；项目在 `00-context/project.md` 的 `framework_version` 中、需求文件在 frontmatter 的 `template_version` 中记录其所依据的规范版本。Skill 的发布版本另行编号，与规范版本的对应关系记录在 Skill 仓库的变更记录中。 |

## 9. 状态与门禁

| 状态 | 含义 | 进入条件 |
|---|---|---|
| `draft` | 起草中 | — |
| `review` | 可供评审 | `prd_lint.py --as review` 无错误；无来源为 `提案` 的条目；审稿无未关闭的 P0 / P1 |
| `frozen` | 可交付开发 | `prd_lint.py` 无错误；无 `[待补充]`、`[待定]`、`[待测]`；权限矩阵无 `?`；「定稿前人工门禁」全部勾选 |
| `deprecated` | 废弃 | 在「本版变更」中说明替代需求 |

| # | 规则 |
|---|---|
| CN-55 | 能由脚本判定的门禁一律由 `prd_lint.py` 判定，不以人工勾选代替。人工门禁只保留脚本无法判定的项目。 |
| CN-56 | 开工条件分两层：**功能开发**不以效果门槛为前提，需求 `frozen` 即可开工；**调优类工作**（模型、Prompt、参数、判定方法等以达到效果门槛为目的的工作）开工前，所引用的验收方案须已冻结，其前置条件（评测集就绪、基线与波动范围已测得、上游契约已冻结）须已到位。上线的效果判定以冻结的验收方案为准。 |
| CN-57 | **验收方案**承载具体门槛，按单个需求或单个发布批次编制，不设全项目共用、可随时变化的门槛。方案带版本号并由 PO 负责；冻结后任何门槛、基线、题集或判定规则的变化都须发布新版本，并注明替代的旧版本。需求中的 `M-n` 引用写作「方案 ID · 版本 · `TH-n`」，引用的条目须存在且指标一致。 |

## 11. 迭代与规则提炼

| # | 规则 |
|---|---|
| CN-70 | 用作精修案例的初稿，须由生成 Skill 在不含其他起草过程的独立会话中生成，并在人工修改前原样提交；否则不作为训练或回归样本。 |
| CN-71 | 人工精修的修改分为**决策类**（回答开放问题、确定口径与取舍）与**非决策类**（补漏、纠正编造、调整结构与表达）。决策类修改回写为开放问题结论，并按影响范围进入项目适配或 ADR，不作为 Skill 规则；只有非决策类修改用于改进 Skill。 |
| CN-72 | 提炼出的规则按层存放：核心规则在 Skill 的 `references/learned-rules-generate.md` 与 `references/learned-rules-review.md`，**只在 Skill 的上游仓库中修改**，项目中的提炼只形成核心规则提案；领域规则在所属领域包的 `learned-rules.md`，项目规则在 `00-context/learned-rules.md`。准入条件：核心规则须在**至少两个不同项目**的案例中出现，只在一个项目中出现的通用经验标为「候选」；领域规则须在至少两份同类需求中出现；项目规则须经需求负责人确认；可由脚本判定的优先实现为 lint 检查。 |
| CN-73 | 规则的新增、修改与删除由需求负责人批准。核心规则变化须提升本文件版本，并在盲测案例上回归；回归结论只在同一规范版本内比较，且须先测出同一版本重复运行的波动范围。 |
| CN-74 | 每次批准并准备对外使用的核心迭代，须同时提升规范版本与 Skill 发布版本，在仓库 `CHANGELOG.md` 记录两者对应关系、迁移影响与回滚目标，并以不可变 Git tag 标记发布提交。已发布 tag 不移动、不覆盖；需要撤销时发布修复版本或对提交执行 `git revert`，项目需求文件不随 Skill 回滚自动降级。 |
