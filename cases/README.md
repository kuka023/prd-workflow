# 精修案例库（Golden Cases）

本目录记录「AI 初稿 → 人工精修」的过程与原因，是 `prd-distill` 提炼规则的唯一依据，也是规范升级后的回归样本。

案例是生成 Skill 持续改进的来源：需求负责人每精修一份需求，就留下一份「初稿哪里不对、为什么这样改」的记录；积累到一定数量后，由 `prd-distill` 从中提炼规则，经批准后回写到对应的层（CN-70 至 CN-73）。

---

## 1. 目录结构

```
cases/<需求ID>/
├── case.yaml       案例元数据：项目、训练 / 盲测、样本类型、规范版本、关键提交、生成器与工作流指标
├── draft-v0.md     prd-generate 的原始输出（只读，不再修改）
└── lessons.yaml    人工精修的修改原因、修改类型与归属层
```

以下内容不在本目录重复存放（避免同一内容存两份）：

| 内容 | 位置 |
|---|---|
| 素材包 | `inputs/<需求ID>/input.md` |
| 生成报告 | `inputs/<需求ID>/generation-report.md` |
| 审稿结果 | `inputs/<需求ID>/review-findings.yaml` |
| 定稿 | `01-requirements/<模块>/<需求ID>-*.md`，定稿提交的 SHA 记在 `case.yaml` |
| 「改了什么」 | Git 提交记录（`git diff <初稿提交>..<定稿提交>`） |

## 2. 样本规划

第一阶段至少 5 个案例，覆盖不同类型的需求；**其中 1–2 个标为盲测（`role: blind`），不参与规则提炼**，只用于检验提炼出的规则在未见过的需求上是否有效。验证通用性时，至少一个案例须来自第二个不同项目。

| 样本类型 | 说明 | 建议角色 |
|---|---|---|
| 含效果验收的主链路 | 业务结果依赖模型能力，需同时验收功能与效果 | 训练 |
| 权限或审批复杂 | 角色多、数据范围限制多、存在审批流转 | 训练 |
| 纯功能配置 | 以配置、维护为主，不含效果验收 | 训练 |
| 时限严格的处置 | 有明确时限、升级与降级要求 | 训练 |
| 业务争议与技术约束并存 | 素材间存在冲突，需要大量开放问题 | 盲测 |

具体需求由需求负责人按素材到位情况确定。**样本的前提是素材真实存在**：没有会议纪要、Demo 或客户材料的需求不适合作为案例。

## 3. 单个案例的操作步骤

| 步 | 操作 | 产出 | 提交信息示例 |
|---|---|---|---|
| 1 | 复制 `inputs/_TEMPLATE/` 为 `inputs/<ID>/`，填写素材包 | `input.md` | `<ID>: 素材包` |
| 2 | 复制 `cases/_TEMPLATE/` 为 `cases/<ID>/`，填写 `case.yaml` 的基本信息 | `case.yaml` | — |
| 3 | **在新会话中**运行 `/prd-generate <ID>`，不做任何人工修改，将需求文件复制为 `cases/<ID>/draft-v0.md` 并提交 | 初稿、生成报告 | `<ID>: AI 初稿（prd-generate，规范 1.2）` |
| 4 | 在新会话或子代理中运行 `/prd-review-refine <ID>` | 审稿结果、修订稿 | `<ID>: 审稿修订` |
| 5 | 人工精修并提交定稿 | 定稿 | `<ID>: 精修——<修改原因概要>` |
| 6 | 运行 `/prd-distill capture <ID>`：比对初稿、修订稿与定稿，起草 `lessons.yaml` 与 `case.yaml` 指标；需求负责人逐条确认 | `lessons.yaml`、`case.yaml` 指标 | `<ID>: 案例归档` |
| 7 | （可选）交给开发或 coding agent 按规格试做，记录停止次数与规格缺口 | `case.yaml` 下游指标 | — |

**第 3 步决定案例是否有效。** 初稿若在已有讨论或草稿的会话中生成，或在提交前做过人工修改，就无法反映 Skill 本身的水平，不作为训练或回归样本（CN-70）。`case.yaml` 的 `draft_generated_in_fresh_session` 记录这一点。

**第 6 步中，需求负责人只需确认三件事**：

1. 修改原因是否准确；
2. 修改类型：**决策类**（回答开放问题、确定口径与取舍）还是**非决策类**（补漏、纠正编造、调整结构与表达）；
3. 非决策类修改的归属层：核心、领域包、项目、lint，或一次性。

决策类修改不用于改进 Skill，而是回写为开放问题结论，进入项目适配或 ADR（CN-71）。

## 4. 规则提炼的准入条件

`prd-distill` 按以下条件决定一条非决策类经验的去向（CN-72）：

| 去向 | 条件 |
|---|---|
| `prd_lint` 检查项 | 可由脚本确定性判定。优先于其他去向 |
| 核心规则（`.claude/skills/<Skill>/references/learned-rules.md`） | 在**至少两个不同项目**的训练案例中出现；不依赖特定领域或客户背景；能写出触发条件、正例、反例与停止条件 |
| 候选核心规则 | 满足核心规则的其他条件，但只在一个项目中出现。记入候选区，不生效 |
| 领域规则（`domain-packs/<包>/learned-rules.md`） | 在至少两份同类产品的需求中出现，且只适用于该类产品 |
| 项目规则（`00-context/learned-rules.md`） | 只适用于本项目，经需求负责人确认 |
| 保留在案例中 | 一次性偏好，或只出现过一次 |

---

## 5. 回归

规则经批准写入后，对盲测案例重新运行 `prd-generate` 与 `prd-review-refine`（`/prd-distill --regress`），比较硬门禁结果、生成器指标与质量维度评级。

- 对比只在同一规范版本内进行（CN-51）。
- 先对同一版本连续运行两次，记录波动范围；新旧版本的差异小于波动范围时，不能认为有改善（CN-73）。
