# 生成阶段 · 从素材包生成 PRD 初稿

> 本文件是 prd-workflow Skill 的阶段说明，由 `SKILL.md` 调度。路径约定：`<SKILL>` 指 Skill 目录；以 `core/`、`stages/`、`templates/`、`references/`、`scripts/` 开头的路径相对 Skill 目录；`00-context/`、`01-requirements/`、`02-contracts/`、`03-quality/`、`04-decisions/`、`inputs/`、`cases/` 相对项目需求库（当前工作目录）。

适配规范版本：**1.5**（`core/constitution.md` 的 `version`）。开始前核对：若 constitution 的版本与此不一致，先告知用户「Skill 与规范版本不一致」，再继续。

## 第一原则

**首稿的价值在于完整且诚实，不在于看起来完整。** 能从素材推出的内容写满并标注来源；推不出的内容留空并给出建议口径。一条编造的业务规则，比十个 `[待补充]` 的危害更大：评审者会因为文档完整而放松，下游 coding agent 会把它当成事实实现。

## 输入

- 需求 ID，如 `/prd-workflow generate ABC-001`。
- 素材包 `inputs/<需求ID>/input.md`（唯一输入，CN-5）。

## 第 0 步：读取上下文

按「核心 → 已启用领域包 → 项目」的顺序读取（CN-8），全部读完再开始：

1. **核心**：`core/constitution.md`（各阶段说明中的 `CN-n` 均指该文件）；`core/guide.md` 中业务闭环与独立能力的边界；共用模板中的「写作说明」与裁剪表；`references/learned-rules-generate.md`（候选区的规则不生效，仅供参考）。
2. **项目声明**：`00-context/project.md`。记下启用的领域包与新增的验收层级；`framework_version` 与当前规范版本不一致时，在报告中注明。
3. **领域包**：`project.md` 的 `domain_packs` 中每个包的 `README.md` 与 `learned-rules.md`，以及与本需求相关的清单（如输入形态、边界示例）。领域包只提供候选与提示，**不作为事实来源**：其中的术语、指标与红线须已登记到项目的 `00-context/` 或 `03-quality/` 才可引用。
4. **项目适配**：`00-context/glossary.md`、`personas.md`、`modules.md`（术语、角色与模块只能从这里取，CN-1）；`00-context/learned-rules.md`；`02-contracts/` 全部文件；`04-decisions/` 中影响本需求的 ADR（未决 ADR 的结论只能作为提案引用，或引用该 ADR 登记 Q-n，不写成事实，CN-4）；本文涉及模型效果时还须读 `03-quality/`，包括覆盖本需求的验收方案（`03-quality/acceptance/`）。
5. **目标需求**：现有文件（`01-requirements/<模块>/<需求ID>-*.md`），保留其 frontmatter 中的 `id`、`title`、`module`、`owner`、`assignee`、`depends_on`、`blocks`、`demo_ref`、`prototype_ref`；以及 `depends_on` 与 `business_requirements` 中的需求。模块用于归档，不从目录或旧 type 字段推断验收方式。

三层规则冲突时，以更具体的一层为准，并在报告中列出冲突（CN-8）。

同时完整读取 `references/module-selection.md`，用于后续选章；领域候选按其触发问题检查，不当作已确认事实。

## 第 1 步：素材包检查

**素材包不存在**：以 `templates/input.md` 为模板创建 `inputs/<需求ID>/input.md`，然后进入「问题定义对话」（见下文），把结果写入 `input.md`。用户仅有模糊想法时同样适用。

**素材包存在**：逐项核对 `input.md` 第 5 节「最低素材检查」。缺项不阻止生成，但对应内容一律以 `[待补充/素材: … — @待定]` 标记，并在报告中列出。

**核对整理内容与原文**（CN-26）：`input.md` 第 1、2、4 节是对素材的整理。逐项检查其中的事实能否在所引 `SRC-n` 的摘录中找到原文。找不到的，视为缺少素材：不作为来源使用，以 `[待补充/素材: …]` 标记并登记 `Q-n`。判断 G-STOP-1 时，只计入能在摘录中找到原文的内容。

### 问题定义对话

目的是在写之前确认这是一个真问题，而不是某一方提出的解决方案。

- **一次只问一个问题**，优先给出单选项，并标明推荐项及理由。
- 依次确认：谁遇到这个问题（角色 ID）→ 有什么证据表明问题真实存在 → 不做会怎样 → 这是问题还是方案。
- 对问题定义提出质疑：素材说「要做 X」时，追问 X 要解决的问题是什么（CN-24）。
- C 级需求须再完成方案比较：提出 2–3 个方案，写明各自的代价，由用户选定；否决的方案与原因写入 `input.md` 第 2 节，作为设计结论的草稿。
- 对话结果写入 `input.md` 第 1、2 节，用户口头确认的内容登记为一个 `SRC-n`（类型「口头确认」，可信度「单方陈述」，注明日期）。

## 第 2 步：规模、规格边界与批次

依据素材包中需求负责人确认的规模、边界与批次，填写 `scale`、`spec_kind`、`batch`。规模未确认时先提出建议并请负责人确认，不自行定级（CN-45）。

- **默认业务 PRD**：`spec_kind: business`，围绕一个主要业务目标说明起点、完成条件与上游前提，不默认合并从数据进入到最终使用的全部路径（CN-46）。
- **可选能力规格**：仅在有复用、独立责任团队或独立评测与发布需要时使用 `capability`。填写拆分理由、输入输出边界与 `business_requirements`；理由未确认时标提案并登记 Q-n。不得仅因涉及 AI 就拆分，也不自动迁移其他组件空壳（CN-52、CN-53）。
- **验收归属**：能力规格指向承担最终业务验收的 PRD，正文注明负责人及其 AC-n / M-n。目标尚未明确时保留 draft、登记 Q-n，不创建虚构 ID；验收归属不写成反向 depends_on。
- **当期批次**：business 检查业务闭环，capability 检查输入到输出承诺；缺少必要环节时准备批次调整建议（CN-49）。
- **效果验收**：逐项判断本期质量承诺；涉及模型效果时保留第 12 章。两种规格均保留功能验收，业务 PRD 不因效果能力已拆出而删除自身效果目标（CN-47）。

- **A 级**：在对话中给出结论（为什么不需要 PRD、建议开发直接处理的范围），**停止**，不生成文件。
- **B 级**：使用统一模板，按模板裁剪表及模块判定精简，不适用时删除，待确认时留下必要问题。
- **C 级**：`input.md` 第 1、2 节未完成时，先进入问题定义对话。

## 第 3 步：停止条件

出现以下任一情形，**停止生成**，按「一次一问、给选项、标推荐」的方式向用户提问：

| # | 情形 |
|---|---|
| G-STOP-1 | 问题定义无法判断：素材中找不到「谁、证据、不做的后果」中的任意两项 |
| G-STOP-2 | 责任边界无法判断：无法明确本文的业务起点与完成条件，或独立能力的输入输出承诺 |
| G-STOP-3 | 素材与 `00-context/` 或 `02-contracts/` 的既有定义冲突 |
| G-STOP-4 | 素材包中没有任何书面素材，只有转述 |

除上述情形及 CN-45 要求的规模确认外不提问，缺口按 CN-30 标记后继续；未确认的拆分方案可作为提案保留在 draft，不扩写其他需求。

## 第 3.5 步：选择条件模块

按 `references/module-selection.md` 的全部模块逐项判断，先在 `inputs/<需求ID>/generation-report.md` 建立「模块适用性」表。已确认事实直接用于选章；重要特征未知写待确认，具体规则未知写 Q-n，不因材料缺失删除模块。除已有停止条件外不暂停要求用户审批选章。

模块可作为功能环节内的小节，也可引用已存在条目；不重复定义、不要求用户面对整套空章节。输入形态、元数据及生命周期独立于效果章节，确定性需求也须判断。

## 第 4 步：生成

以模块模板 `templates/requirement-prd.md` 为骨架，覆盖写入目标需求文件。逐章按模板中的「写作说明」撰写，以下是生成时的硬性要求：

**来源（CN-20 至 CN-25）**
- CN-20 所列的每个条目都要填「来源」，取值只能是 `SRC-n` / `CTX` / `Q-n` / `提案`。
- 标 `SRC-n` 前，确认该素材的原文确实支撑这条内容；只是「相关」不算支撑。
- 标 `CTX` 前，确认所依据的上下文条目已确认（其来源为 `PS-n` 或已有结论的 `Q-n`）。上下文条目仍为 `提案` 时，本条来源写 `提案`，并在报告「假设」中注明依据的上下文条目（CN-9、CN-21）。
- 素材中没有依据、但为保持文档连贯确需给出的决策层内容，标为 `提案`，并在报告的「假设」中逐条列出。**不得以 `SRC-n` 或 `CTX` 冒充来源。**
- 连合理提案都给不出的，写 `[待补充/类别: 问题 — @负责人]`，并在开放问题表登记 `Q-n`，给出建议口径（CN-31）。
- 数字没有来源时，写 `[待定]` 或 `[待测]`，不填估计值（CN-23）。
- 正文引用素材时保留稳定编号，并写成 `SRC-n · [业务可读名称](#src-n)`。业务可读名称取自素材标题或能准确区分素材的中性短名，不把 AI 的解释写进名称（CN-27）。`CTX`、`Q-n` 与「提案」仍按 CN-21 原样标注。

**内容**
- 设计结论优先取自 `input.md` 第 2 节。B 级素材包没有第 2 节时，从素材中已确认的取舍提取（来源 `SRC-n`）；素材中没有取舍的，至少以 `提案` 写出一条，并附一个被否决的备选方案。每条都要写明「接受的代价」与「复议条件」。
- 一个条目的不同部分来源不同时，按 CN-21 写作 `SRC-1（结论）、提案（复议条件）`。表格「来源」列之外的正文内容，用行内「（来源：提案）」标注，不写「提案：」。
- 本期范围按可验收的结果划分：business 是业务结果，capability 是输入输出承诺，不按技术层拆成无法验收的片段。
- 闭环全景写本文边界与端到端验收场景，并使用 Mermaid `flowchart` 表达主路径、结果分流、失败处置及必要回边；不得用一行箭头文本代替。图中节点名称与环节表、第 8 章保持一致，只写产品流程，不写技术组件。功能需求按环节展开；能力细节已在其他规格定义时引用其编号，不复制。验收责任与归属表说明谁负责最终业务验收。
- 功能验收至少有一条贯穿本文责任边界的端到端验收（CN-44）；每个 `BR-n`、`DR-n`、`EX-n`、功能条目都要有 AC 覆盖。能力规格同样验收确定性约束，不能只填效果指标。AC 依据已溯源条目编写（CN-43），填写验证层级。
- 有跨需求路径时，指定业务 PRD 中的集成 AC 与负责人；本文不是承接方时引用该 AC。业务级效果与局部能力效果分别验收，不能以组件通过替代整体通过。
- 按模块选择展开配置、输入、元数据、任务与输出、记忆、行动、人工、生命周期、效果、运行、预算与反馈。效果验收聚焦质量定义、失败代价、场景代表性和评测协议；输入行为独立写在功能需求。所有具体行为使用稳定编号并纳入 AC，辅助表引用编号。
- **门槛、基线与波动范围不写入需求**（CN-3、CN-57）。覆盖本需求的验收方案已存在时，`M-n` 的门槛引用写作「方案 ID · 版本 · TH-n」，且指标 ID 与方案条目一致；不存在时写 `[待定]`，登记 Q-n，并在报告中建议 PO 建立验收方案。素材中出现的门槛数字写入 Q-n 的建议口径，由 PO 决定是否写入方案；本阶段不创建或修改验收方案。
- 启用的领域包提供输入形态等候选清单时，只选取与本需求相关、且素材中有依据的项；没有依据的形态不写入。
- 验证层级取核心层级（界面、接口、数据、评测）或 `project.md` 中新增的层级。
- 失败后的继续、拒答、停止或人工处置须有依据；不得默认所有效果组件失败都可跳过。确定性约束仍编写功能 AC。
- 后续批次的能力写入非本期范围，标注目标批次；当期批次无法自成闭环时，在开放问题中提出批次调整建议（CN-49）。
- 与其他闭环的依赖写入 2.4 节，并在 frontmatter 声明 `depends_on`。
- 保留模板中通用的 `STOP-n`，并补充本需求特有的停止情形。
- 附录「依据素材」与 `input.md` 的素材清单保持一致：15.1 提供素材总览，15.2 为每个 `SRC-n` 建立同名锚点和来源卡片。卡片从素材清单与摘录中填写原文位置、材料性质、关键摘录、本需求用法和不直接支撑的边界；原文位置有稳定路径或 URL 时写成可点击链接，没有可共享链接时如实说明，不伪造或搬运受限材料（CN-27）。
- 素材中出现 `00-context/` 未登记的术语或角色时，不修改 `00-context/`，以 `[待补充/术语: …]` 提出并在建议口径中给出定义（CN-1）。
- 生成中发现本需求依赖其他需求的，在第 5 章登记 `DEP-n`（注明来源），在本需求 frontmatter 的 `depends_on` 中加入对方 ID，并在对方需求 frontmatter 的 `blocks` 中加入本需求 ID。对方文件只允许修改 `blocks` 这一个字段。依赖关系本身没有素材依据的，来源标 `提案`。
- 不修改素材包判定的规模。认为判定不当的，在报告中提出理由。
- 不写代码路径、代码片段、技术选型（CN-36），不描述视觉样式（CN-37），不用代词（CN-35），不用禁用同义词。

**收尾**
- 整块删除全部以「**写作说明**」开头的引用块（CN-39）。
- 删除不适用章节和槽位，在报告保留判断依据；待确认项登记 Q-n，不留整套空表。填写模块适用性表的真实正文与验收编号、相关 Q-n，然后再运行自检（CN-48、CN-58）。
- frontmatter：`status: draft`，`template_version` 填当前规范版本，`updated` 填当天日期。

## 第 5 步：自检

运行：

```bash
python3 <SKILL>/scripts/prd_lint.py --file <需求文件>
```

- 只修复机械性问题：编号、格式、类别标签、遗漏的 AC 覆盖、引用写法。
- **来源类错误（SR01、SR02）不得以补写来源的方式消除**：内容确有依据的，写明真实来源；没有依据的，改标 `提案` 或退回 `[待补充]`。
- 再运行一次 `--as review`，记录距离 review 还差什么，写进报告。

## 第 7 步：交接

- 若 `cases/<需求ID>/` 存在（精修案例），将需求文件复制为 `cases/<需求ID>/draft-v0.md`。
- 建议用户**在任何人工修改之前**原样提交：`<需求ID>: AI 初稿（生成阶段，规范 1.5）`。是否提交由用户决定。
- 本次会话若在生成前已有其他起草或讨论，在报告与对话中注明：该初稿不满足 CN-70，不宜作为精修案例的 `draft-v0`。
- 提示下一步：审稿。由 `/prd-workflow new` 全流程调用时，审稿在另一个独立子代理中进行；单独调用本阶段时，提示用户**在新会话中**运行 `/prd-workflow review <需求ID>`。审稿不应沿用本次生成的推理过程，否则生成与审稿会有相同的盲区。
