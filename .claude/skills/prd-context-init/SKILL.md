# prd-context-init · 项目适配初始化与更新

适配规范版本：**1.2**。开始前核对 `constitution.md` 的 `version`，不一致时先告知用户。

## 第一原则

**项目适配是所有需求的共同依据。** 需求中标注 `CTX` 的内容，最终都追溯到这里；这里的一条编造，会以「已确认的上下文」的身份进入每一份需求。因此本 Skill 起草的每个条目都要能指向一份项目素材；指不出来的，标为提案，等待确认。

**提案，而不是提问。** 需要用户决定的事项，先给出草拟结论与理由，请用户确认或修改；不向用户罗列空白问题。

## 模式

| 调用 | 行为 |
|---|---|
| `/prd-context-init` | 初始化：从项目素材起草全部项目适配文件，输出确认清单 |
| `/prd-context-init --update` | 增量更新：登记新素材，只提出新增与变化的条目，不改动已确认条目 |
| `/prd-context-init --confirm` | 回写确认：把用户对确认清单的答复写回各文件，更新来源与状态 |

## 第 0 步：读取

1. `constitution.md`：重点是 CN-1 至 CN-3、CN-7 至 CN-10、第 3、4 节与第 6 节。
2. `FRAMEWORK.md`：哪些文件属于项目适配。
3. 项目适配的全部现有文件：`00-context/`（含 `project.md`、`sources.md`）、`02-contracts/`、`03-quality/`。它们是骨架时，按骨架的表格结构填写，不另起格式。
4. `domain-packs/` 下每个包的 `README.md`，用于判断是否建议启用。
5. `01-requirements/_GUIDE.md`：业务目标划分的方法，用于起草候选需求清单。

## 第 1 步：收集与登记素材

请用户提供项目已有文档的路径或目录，例如既有 PRD、用户旅程、系统说明、组织与角色清单、数据字典、会议纪要、客户材料、原型说明。只有口头描述时，先以一次一问的方式问清项目目标、用户角色与主要业务目标，并登记为「口头确认」素材。

逐份阅读，在 `00-context/sources.md` 中登记为 `PS-n`：类型、名称、位置、日期、提供方、可信度、覆盖内容。每份素材在「关键摘录」中保留后续条目所依据的原文（脱敏）。**原件不复制入库。**

**迁移已有项目时**：已有的 `00-context/` 等文件本身作为素材登记（类型「既有上下文」）。其中已由决策方确认的内容，可信度按原确认方式填写；来历不明的内容按「单方陈述」处理。

**停止条件**：

| # | 情形 | 处理 |
|---|---|---|
| C-STOP-1 | 找不到任何书面素材，用户也无法口头说明项目目标与用户角色 | 停止，说明需要哪些素材 |
| C-STOP-2 | 素材之间对产品定位或主要用户存在根本冲突 | 停止，列出冲突双方的原文，请用户裁定后再继续 |

## 第 2 步：起草

按下表逐个文件起草。**每一行都填「来源」**：有素材原文支撑的写 `PS-n`；没有的写 `提案`，并在 `project.md` 的「项目适配待确认事项」表中登记 `Q-n`、给出建议口径；连提案都给不出的写 `[待补充/类别: 问题 — @负责人]` 并登记 `Q-n`（CN-9、CN-30、CN-31）。

| 文件 | 起草内容 | 谁拍板 | 要点 |
|---|---|---|---|
| `project.md` | 项目目标与范围；`domain_packs`；`verification_levels`；最低项目上下文的状态 | 目标与范围：业务。领域包与验收层级：我方 | 领域包只在产品类型明确匹配时建议启用，理由写入报告 |
| `modules.md` | 模块、需求 ID 前缀、名称、范围 | 我方 | 模块用于归档，按系统或职能边界划分即可；前缀 2–6 位大写字母，一经使用不得更改 |
| `glossary.md` | 业务概念、定义、禁用同义词；不同素材对同一概念的不同叫法写入命名映射 | 业务 | 同一概念在素材中叫法不一致时，列出各处叫法，建议统一用词，登记 Q-n；不自行裁定 |
| `personas.md` | 角色 ID、名称、职责；动作权限矩阵 | 业务（合规相关的另列合规方） | 角色 ID 形如 `R-XXX`；素材未说明的权限格填 `?`，不推断 |
| `02-contracts/data-model.md` | 核心实体、状态机、跨实体约束 | 我方（业务含义由业务确认） | 只写素材中出现的实体与状态；字段只在素材有数据字典时填写 |
| `03-quality/metrics.md` | 全局红线；产品含模型能力时的指标口径 | 红线：业务与合规。口径：PO | 启用领域包时，可从 `metrics-seed.md` 选取候选，来源一律为 `提案` |
| `03-quality/nfr.md` | 全局非功能要求 | 我方与 IT | 数字无来源时写 `[待定]` |
| `03-quality/eval-sets.md` | 已存在的评测集登记 | PO | 只登记确实存在的评测集，不预设 |

**不起草的内容**：

- **验收方案**（`03-quality/acceptance/`）：门槛由 PO 决定（CN-57）。只在报告中建议需要建立哪些方案、按需求还是按批次划分。
- **需求文件正文**：由 `prd-generate` 负责。本 Skill 只提出候选需求清单（第 3 步）。
- **项目规则**（`00-context/learned-rules.md`）：只来自精修案例，保持为空。

**纪律**：

- 不得以 `PS-n` 标注素材原文不支撑的内容；只是「相关」不算支撑（CN-9、CN-25）。
- 素材中出现的「要做 X」是需求主张，不是项目适配，写入候选需求清单而不是术语或规则。
- 数字（人数、容量、时限、比例）必须有来源，否则写 `[待定]`（CN-23）。
- 领域包条目进入项目文件时，来源为 `提案`，并在说明中注明取自哪个领域包。

## 第 3 步：候选需求清单

依据 `_GUIDE.md`，按主要业务目标提出候选需求划分，写入报告（不创建需求文件）：

| 候选 ID | 名称 | spec_kind | 业务起点 → 完成条件 | 主要角色 | 建议批次 | 依据 | 待确认 |
|---|---|---|---|---|---|---|---|

- 默认 `business`；只在素材显示复用、独立团队或独立评测与发布需要时建议 `capability`，并写明理由（CN-52）。
- 指出跨需求的集成验收建议由哪份业务 PRD 承担。
- 迁移已有项目时，与既有需求 ID 对照：保留、合并、拆分或废弃的建议逐条列出，既有 ID 不重编号（CN-10）。
- 批次与划分属于范围决策，全部作为提案，由需求负责人与业务方确认。

## 第 4 步：自检

```bash
python3 scripts/prd_lint.py
python3 scripts/generate_status.py
```

- 修复 CX 类问题中的机械性问题（编号格式、未登记的 `PS-n`）。**来源不实的问题不得以补写来源的方式消除。**
- `decisions.md` 第 5 节列出项目适配中全部待确认的提案，核对与确认清单一致。

## 第 5 步：报告与确认清单

写入 `inputs/_project/context-init-report-<日期>.md`，在对话中给出摘要：

```markdown
# 项目适配初始化报告 <日期>

- 规范版本 / 模式（初始化 / 更新）/ 登记素材数

## 1. 素材覆盖
| 项目适配内容 | 已有素材支撑 | 缺口 |

## 2. 确认清单（按决策方分组）
### 业务方
| Q-n | 事项 | 草拟结论 | 理由与依据 | 影响哪些文件 |
### 我方（需求负责人可直接确认）
| Q-n | 事项 | 草拟结论 | 理由 |
### PO / IT / 合规

## 3. 建议启用的领域包与验收层级

## 4. 候选需求清单

## 5. 建议建立的验收方案

## 6. 开始生成需求前还缺什么
按「不补则生成时会大量出现待补充」的程度排序。
```

确认清单遵循「分清谁拍板」：术语口径、角色权限、红线、范围与批次由业务方确认；模块划分、前缀、验收层级、文件组织由我方决定，以草拟结论的形式请需求负责人「看一眼改」。

## 第 6 步：回写确认（`--confirm`）

用户对确认清单逐项答复后：

1. 将结论写入 `project.md` 待确认事项表的「结论」列。
2. 回写到对应条目：内容按结论修改，来源由 `提案` 改为该 `Q-n`。用户同时提供了书面依据的，登记为新的 `PS-n` 并改用 `PS-n`。
3. 口头确认的，登记一份「口头确认」素材（注明确认人与日期），可信度「单方陈述」或「会议共识」。
4. 更新 `project.md`「最低项目上下文」表的状态。
5. 用户确认候选需求清单后，可按清单创建需求文件，**只写 frontmatter**（`id`、`title`、`module`、`spec_kind`、`batch`、`owner`、`status: draft`、`template_version`），正文由 `prd-generate` 生成。
6. 再次运行第 4 步自检。

## 增量更新（`--update`）

- 只登记新素材，并对照已有条目提出新增、修改与冲突。
- **已确认的条目（来源为 `PS-n` 或已有结论的 `Q-n`）不直接修改**：新素材与之冲突时，登记新的 `Q-n`，写明新旧依据，由决策方裁定。
- 被修改的术语、角色或实体若已被需求引用，在报告中列出受影响的需求 ID。
