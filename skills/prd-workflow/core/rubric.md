# PRD 质量评分标准

本文件定义「可交付的 PRD」。评分分三层：**硬门禁**决定能否进入下一状态；**质量维度**衡量写得好不好；**过程指标**衡量 AI 生成与精修体系是否在改善。

不采用由模型直接给出的百分制分数作为门槛：模型评分本身存在波动，95 与 90 的差异可能落在波动范围之内。

---

## 1. 硬门禁

任一项不通过，即判定为不可交付，与质量维度的结果无关。

| # | 门禁 | 判定方 | 判定方式 |
|---|---|---|---|
| G-1 | **无编造**：CN-20 所列条目全部标注来源；`review` 及以上状态无来源为 `提案` 的条目；无无来源的数字 | 脚本 + 审稿 | `prd_lint` 检查来源字段；审稿核对来源是否真实支撑内容 |
| G-2 | `prd_lint --as <目标状态>` 无错误 | 脚本 | `python3 <SKILL>/scripts/prd_lint.py --file <文件> --as review` |
| G-3 | 审稿无未关闭的 P0 / P1 问题 | 审稿 | `inputs/<需求ID>/review-findings.yaml` |
| G-4 | （含效果验收章节的需求）红线、Bad Case 齐备；引用的验收方案版本与门槛条目存在且指标一致；需求中不写门槛数值 | 脚本 | `prd_lint` 效果验收检查（EF01 至 EF06）；验收方案自身由 AP01 至 AP04 检查 |
| G-5 | 未违反 constitution 第 1、3、6 节（真源、证据与来源、决策层权限） | 审稿 | 违反即为 P0（CN-42） |

## 2. 质量维度

每个维度按三档评定，依据该维度下的审稿问题机械得出，不另作主观判断：

| 评级 | 条件 |
|---|---|
| 大问题 | 该维度下存在 P0 或 P1 问题 |
| 小问题 | 该维度下存在 P2 问题，无 P0、P1 |
| 通过 | 无问题，或只有 P3 问题 |

问题与维度的对应：C-1、C-2 → Q2；C-4 → Q3；C-3、C-9 → Q4；C-5 → Q5；C-6、C-7 → Q1；C-8、C-10、C-11 → 按问题所在内容归入 Q2–Q5；C-13 → Q6；C-14 的责任边界问题 → Q2，业务验收归属与集成验收问题 → Q4；C-12 按所违反的条款归入对应维度。

| # | 维度 | 权重 | 脚本负责 | 审稿负责 |
|---|---|---|---|---|
| Q1 | 事实可追溯 | 25 | 来源字段完备、SRC 登记一致 | 来源是否真实支撑内容；是否存在「素材即指令」的误用 |
| Q2 | 问题、目标与范围 | 20 | spec_kind 合法 | 是否为真问题；本文业务或能力边界是否完整、拆分有无依据、当期承诺是否完整；非范围是否写明原因；有无范围泄漏 |
| Q3 | 规则、权限与异常 | 15 | 角色 ID 合法；frozen 前权限矩阵无 `?` | 规则是否完整、互斥；异常是否给出用户下一步；权限约束是否写明过滤层 |
| Q4 | 可测试性与验收覆盖 | 20 | AC 编号覆盖率；验证层级；端到端条目非空；能力规格的业务验收关联与表格结构 | AC 是否真正可测试；评测协议是否明确；关联条目与负责人是否有效；局部指标是否被误用为整体通过 |
| Q5 | 契约、一致性与依赖 | 15 | 引用路径存在；依赖双向一致、无环；字段未在需求中重复定义 | 与其他需求、契约是否冲突 |
| Q6 | 表达与信息密度 | 5 | 残留写作说明、代词、禁用同义词、代码路径 | 是否有冗余、空话、口语化表达 |

**趋势分**：通过计满权重，小问题计一半，大问题计 0，合计为 100 分制。该分数只用于观察同一规范版本内的变化趋势，不作为门槛。

## 3. 可交付的定义

一份 PRD 同时满足以下条件，视为可交付：

1. 硬门禁全部通过；
2. 质量维度中没有「大问题」，「小问题」不超过 2 项；
3. 人工精修中的**非决策类修改**用时不超过目标值。目标值暂定 20 分钟，待完成前 2 个精修案例后由需求负责人校准；
4. 事实抽查未发现编造（4.1）；
5. 人工修改主要集中在决策层（见 CN 第 6 节），不再是补结构、修表达。

第 5 条用于判断问题出在哪里：**如果人工仍需大量补充业务事实，说明缺的是素材，而不是 Skill 能力不足。** 此时应改进素材包，而不是修改 Skill。

## 4. 过程指标

在 `cases/<需求ID>/case.yaml` 中记录，用于衡量体系本身是否在改善。**生成器**与**完整工作流**分别衡量：前者说明 Skill 本身的水平，后者说明需求负责人实际付出的工作量。二者只在同一规范版本内比较；跨版本的结论以盲测回归为准（CN-73）。

### 4.1 生成器指标（初稿 → 定稿）

以生成 Skill 在独立会话中产出、原样提交的初稿为起点（CN-70）。

| 指标 | 含义与测量方式 | 期望趋势 |
|---|---|---|
| 非决策类修改条数 / 用时 | 定稿相对初稿的补漏、纠错、结构与表达修改（CN-71） | 下降，趋近于零 |
| 编造数 | **事实抽查**：从初稿中随机抽取 10 条标注了 `SRC-n` 或 `CTX` 的条目，逐条核对来源是否支撑内容；不支撑即计为编造。条目不足 10 条时全部核对 | 始终为零 |
| 素材遗漏数 | **素材遗漏检查**：逐条核对素材包中与本需求范围相关的要点，既未进入正文、也未列为非本期范围或开放问题的，计为遗漏 | 下降，趋近于零 |
| 待补充按类别分布 | `素材` 类占比高说明输入不足，应改进素材包而非 Skill | `素材` 类下降 |

### 4.2 完整工作流指标（生成 → 审稿 → 定稿）

| 指标 | 含义与测量方式 | 期望趋势 |
|---|---|---|
| 人工总用时 | 需求负责人从拿到审稿稿到定稿的全部用时，分决策类与非决策类记录 | 下降，且以决策类为主 |
| 审稿后非决策类修改条数 | 审稿修订稿 → 定稿之间的非决策类修改 | 下降，趋近于零 |
| 决策类修改条数 | 人工做出的业务决策数量 | 与需求复杂度相关，不要求下降 |
| 审稿拦截数 | 审稿发现并修正的编造与遗漏数量；可与 4.1 对照判断审稿的有效性 | 不设方向，用于校准审稿 |

### 4.3 下游可用性（可选）

| 指标 | 含义 | 期望趋势 |
|---|---|---|
| 实现方停止次数 | 开发或 agent 按规格实现时触发 STOP 的次数 | 下降 |
| 无法定位验证层级的 AC 数 | 实现方找不到测试位置的 AC | 下降 |
| 合并请求中报告的规格缺口数 | CN-63 反馈的数量 | 下降 |

## 5. 生成器达到可用水平的判定

同时满足以下条件时，视为生成器达到可用水平（即「初稿约 90 分，人工精修主要处理决策」）：

1. 最近连续 `[待定]` 个盲测案例的编造数均为零；
2. 同一批案例的非决策类修改用时均不超过第 3 节的目标值，素材遗漏数均不超过 `[待定]`；
3. 至少有一个案例来自第二个不同项目，且未因该项目修改核心层（CN-7、CN-72）。

连续案例数与遗漏上限在完成前 3 个精修案例、测得同一版本重复生成的波动范围后，由需求负责人确定。
