# 检查阶段 · 确定性检查

> 本文件是 prd-workflow Skill 的阶段说明，由 `SKILL.md` 调度。路径约定：`<SKILL>` 指 Skill 目录；以 `core/`、`stages/`、`templates/`、`references/`、`scripts/` 开头的路径相对 Skill 目录；`00-context/`、`01-requirements/`、`02-contracts/`、`03-quality/`、`04-decisions/`、`inputs/`、`cases/` 相对项目需求库（当前工作目录）。

适配规范版本：**1.3**。

## 运行

| 目的 | 命令 |
|---|---|
| 检查全库（含验收方案） | `python3 <SKILL>/scripts/prd_lint.py` |
| 检查一份需求 | `python3 <SKILL>/scripts/prd_lint.py --file <需求文件>` |
| 预检能否提交评审 / 定稿 | `python3 <SKILL>/scripts/prd_lint.py --file <需求文件> --as review`（或 `--as frozen`） |
| 供其他 Skill 读取 | 追加 `--json` |
| 只看错误 | 追加 `--errors-only` |

同一检查项在 `draft` 状态多为警告，在 `review`、`frozen` 状态为错误。用户问「能不能提交评审」时，使用 `--as review`。

## 检查项

| 代码 | 内容 | 规则 |
|---|---|---|
| FM01–FM05 | frontmatter 字段、取值（含 scale、batch）、文件名与目录一致、规范版本、ID 重复 | CN-10、CN-49、CN-50 |
| SK01–SK03 | spec_kind；能力规格的业务验收关联须为 ID 列表且指向有效业务 PRD；归属表须列负责人及 AC-n / M-n | CN-48、CN-53 |
| DP01–DP03 | 依赖指向存在、双向声明、无依赖环 | — |
| ST00–ST03 | 未展开、必填章节、残留写作说明、空章节 | CN-39、CN-48 |
| TD01–TD05 | 待补充的类别与负责人、frozen 不得有待补充与待定值、未知项须有 Q-n | CN-30 至 CN-33 |
| SR01–SR07 | 来源缺失、取值非法、未决提案、SRC 与素材包不一致、以未决 Q-n 为来源、「提案」未使用规定写法 | CN-20 至 CN-22 |
| RF01–RF07 | 孤儿编号、重复定义、路径不存在、角色未登记、需求 ID 不存在、指标与评测集未登记、跨文件引用的编号（如「ABC-001：AC-2」）在目标需求中不存在 | CN-1、CN-3、CN-11、CN-53 |
| QS01–QS02 | 开放问题缺建议口径、负责人、时限 | CN-31、CN-32 |
| PM01 | 权限矩阵存在 `?` | — |
| CV01–CV04 | AC 编号覆盖、验证层级（核心层级加 `00-context/project.md` 声明的层级）、AC 未填覆盖、端到端条目的 Given / When / Then 非空；语义有效性由审稿判断 | CN-8、CN-44 |
| EF01–EF06 | 含效果验收章节时：引用验收方案（EF01）、红线（EF02）、质量指标及门槛引用写法，需求中不得出现门槛数值列（EF03）、Bad Case（EF04）、定稿时所引方案未冻结的提示（EF05，仅提示）、门槛引用可解析：方案版本与 TH-n 存在且指标一致，已被取代的版本给出警告（EF06） | CN-3、CN-56、CN-57 |
| CX01–CX03 | 项目适配条目（`00-context/`、`02-contracts/`、`03-quality/`）的来源：缺失或取值非法（CX01）、`PS-n` 未在 `sources.md` 登记或 `Q-n` 不在 `project.md` 待确认事项中（CX02）、以未决 `Q-n` 为来源（CX03） | CN-9 |
| AP01–AP04 | 验收方案：frontmatter 与适用范围（AP01）、覆盖的需求及指标、评测集已登记（AP02）、门槛条目完整、有来源，冻结后无待定值与提案（AP03）、版本重复或同一方案存在多个冻结版本（AP04） | CN-57 |
| WR01–WR04 | 代码路径或代码块、代词、禁用同义词、章节号引用 | CN-13、CN-35、CN-36 |

## 修复原则

**只修复机械性问题**：编号、格式、类别标签、引用写法、遗漏的 AC 覆盖（依据已溯源条目编写，CN-43）、残留写作说明、空章节的删除。

**以下问题不得以「让 lint 通过」为目的修改**：

| 代码 | 正确处理 |
|---|---|
| SR01、SR02 | 内容确有依据的，写明真实来源；没有依据的，改标 `提案` 或退回 `[待补充]`。**不得补写来源。** |
| SR03、SR07 | 提案须由人决策。SR07 先把写法改为「（来源：提案）」；然后列出全部提案及对应 `Q-n`，交给需求负责人。 |
| TD01、TD04、PM01、EF05 | 这些是待决事项，不是格式问题。列出清单，交给对应负责人。 |
| EF03、EF06、AP03 | 门槛与基线由 PO 在验收方案中确定。不得为消除错误而在需求或方案中填写数字；未定时写 `[待定]` 并登记 Q-n。 |
| CX01–CX03 | 项目适配的来源问题通过初始化阶段处理：有素材的登记 `PS-n`，没有的改标 `提案` 并登记 `Q-n`。不得为消除问题补写来源。 |
| RF07 | 目标需求中确实没有该条目的，登记 Q-n 请双方负责人确认，不在目标文件中代为新增条目。 |
| SK01–SK03 | 不得猜测规格类型或业务验收归属，也不得把旧需求自动标为 business 以消除错误；缺依据时登记 Q-n，由负责人确认。 |
| WR03 | 禁用同义词若出现在专有名词中（如产品或系统的正式名称），属于术语表需要澄清的问题，报告给用户，不强行替换。 |

## 报告

向用户报告时：

1. 先给结论：能否进入目标状态。
2. 列出错误，按「可以直接修复」与「需要人决策」两类分开。
3. 附上脚本输出末尾的统计：待补充按类别分布、提案数、AC 覆盖率。
