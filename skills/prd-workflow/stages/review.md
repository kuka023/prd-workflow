# 审稿阶段 · 独立审稿与修订

> 本文件是 prd-workflow Skill 的阶段说明，由 `SKILL.md` 调度。路径约定：`<SKILL>` 指 Skill 目录；以 `core/`、`stages/`、`templates/`、`references/`、`scripts/` 开头的路径相对 Skill 目录；`00-context/`、`01-requirements/`、`02-contracts/`、`03-quality/`、`04-decisions/`、`inputs/`、`cases/` 相对项目需求库（当前工作目录）。

适配规范版本：**1.5**。开始前核对 `core/constitution.md` 的 `version`，不一致时先告知用户。

## 第一原则

**审稿者的职责是找出问题，不是把文档改漂亮。** 措辞通顺、结构完整的文档仍可能是错的。审稿要回答三个问题：这是真问题吗？每一条内容都有依据吗？开发拿到后能否不做任何产品决定就开工？

## 独立性要求

审稿必须在**不含生成过程**的上下文中进行，否则生成器与审稿器共享同样的盲区。

- 若当前会话中已运行过生成阶段或以其他方式参与了该需求的起草，**使用子代理执行本阶段**：只传入需求 ID、项目目录与 `stages/review.md` 的路径，不传入生成时的推理、对话或结论。
- 审稿依据的是文件，不是生成者的解释。

## 模式

| 调用 | 行为 |
|---|---|
| `/prd-workflow review <ID>` | 默认：审稿 → 修订 → 记录；评分针对修订前的版本 |
| `/prd-workflow review <ID> --no-edit` | 只输出问题清单，不修改需求文件 |
| `/prd-workflow review <ID> --score-only` | 只做门禁判定与质量维度评级。用于修订后的独立评分，须在新的子代理中运行 |

## 第 0 步：读取

按「核心 → 已启用领域包 → 项目」的顺序读取（CN-8）：

1. `core/constitution.md`、`core/rubric.md`，以及需求所用模板中的「写作说明」。
2. `references/review-checklist.md`、`references/module-selection.md` 与 `references/learned-rules-review.md`（候选区不生效，仅供参考）。
3. `00-context/project.md`；其中启用的每个领域包的 `README.md` 与 `learned-rules.md`。
4. `00-context/`（含 `learned-rules.md`）、`02-contracts/`、`04-decisions/` 中影响本需求的 ADR；含效果验收章节的加读 `03-quality/`，以及需求引用的验收方案。
5. 需求文件本身、`core/guide.md`，以及 `depends_on`、`blocks`、`business_requirements` 中的相关需求。按 spec_kind 判断本文责任边界，不按旧 type 字段决定是否审查效果。
6. **暂不读取** `inputs/<需求ID>/input.md` 和生成报告中的选章理由，先完成第 2 步冷读；lint 返回的结构性发现不作为语义判断依据。

## 第 1 步：确定性检查

```bash
python3 <SKILL>/scripts/prd_lint.py --file <需求文件> --as review --json
```

lint 报告的问题分两类处理：

- **待决事项**：SR03（未决提案）、PM01（权限矩阵 `?`）、TD01、TD04、MS04（模块问题尚未回写）、EF05（引用的验收方案未冻结）、门槛引用为 `[待定]` 的 `M-n`。它们表示「还需要人决策或回写」，不是审稿问题，不记入问题清单，汇总到报告的「需要人来决策的事项」。
- **其余问题**：直接记入问题清单（`found_by: lint`），按 CN-41 定级，不再重复判断。lint 能查的内容，审稿不在其上花时间。

## 第 2 步：冷读测试

只凭需求文件与 `00-context/`、`02-contracts/` 阅读全文，把**无法读懂或必须猜测才能实现**的地方逐条记下：指代不明、依赖未说明的背景、判定条件不完整、「合理」「及时」这类无法执行的词。

每一处都是一个问题（通常为 P2；导致实现方须自行做产品决定的为 P1）。

对照模块目录独立记录本文应考虑的能力特征；不从生成器选择倒推正确答案。

## 第 3 步：证据核对

读取 `inputs/<需求ID>/input.md`，对所有标注来源的条目逐条核对：

| 情形 | 判定 |
|---|---|
| 来源为 `SRC-n`，但素材原文不支撑该内容 | **P0 编造** |
| 来源为 `CTX`，但 context 或契约中没有对应定义 | **P0 编造** |
| 来源为 `CTX`，但对应的上下文条目来源为 `提案`（CN-9） | P1：改标 `提案`，与该上下文条目的 `Q-n` 关联 |
| 素材中的「要做 X」被直接写成需求，未经问题定义 | P1（CN-24） |
| 数字无来源，或来源不含该数字 | **P0 编造** |
| 来源为 `提案` | 不是错误；在报告中列出，提醒须在 review 前决策 |

同时检查业务可读性（CN-27）：正文中的 `SRC-n` 是否带有准确的业务可读名称并可跳转到来源卡片；卡片能否打开或明确定位原文，是否区分材料性质、实际支撑与不支撑的边界。名称、摘录或边界超出素材时，仍按来源不实处理，不以“方便阅读”为由补写。

## 第 3.5 步：素材遗漏检查

逐条阅读素材包中的素材摘录，找出与本需求范围相关、但**既未进入正文，也未列为非本期范围或开放问题**的要点。

| 情形 | 判定 |
|---|---|
| 遗漏的要点是业务规则、权限、异常处置、验收口径或红线 | P1（实现方会漏做，或须自行决定） |
| 遗漏的要点属于表达层细节 | P2 |
| 素材要点与本需求范围无关 | 不记录 |

记录时写明遗漏的 `SRC-n` 与原文要点。修订时不直接把遗漏内容写成事实：素材原文支撑的补入正文并标注来源；需要取舍的登记 Q-n。遗漏数单独统计，写入报告，供 `case.yaml` 的 `review_caught` 使用。

随后读取生成报告「模块适用性」表，与自己的判断比较。核对不适用是否有真实范围依据、适用但缺规则是否被错误删掉、适用内容是否落实到正文和验收，以及输入/元数据/生命周期是否因无效果章节而遗漏。具体证据充分时修正选章；业务取舍缺失时保留问题，不扩写承诺。

## 第 4 步：逐项审查

按 `references/review-checklist.md` 的 14 类逐项审查，每发现一个问题记一条。清单之外发现的问题同样记录，类别写「其他」。

闭环全景须使用 Mermaid `flowchart`。审稿时核对图中的主路径、分支、失败处置和回边是否与环节表、第 8 章及异常章节一致；只有线性箭头文本、图表语义不一致或在图中混入技术实现时，按实际影响记录问题。

业务 PRD 与能力规格均检查确定性行为；涉及模型效果时检查评测协议、效果目标，以及门槛是否只以「方案 ID · 版本 · TH-n」引用、引用的方案是否覆盖本需求（CN-57）。拆分后重点核对最终业务验收归属、端到端集成与局部指标的关系。lint 检查关联 ID 和表格结构，审稿核对目标条目是否存在、责任是否有效、指标是否真正覆盖业务目标。

## 第 5 步：记录问题

写入 `inputs/<需求ID>/review-findings.yaml`，格式见 `templates/review-findings.yaml`。每条包含：编号、严重度（CN-41）、类别、位置、问题、理由、处理方式（直接修改 / 提出建议）、状态。

严重度的判定以 CN-41、CN-42 为准。注意区分：决策层内容无依据为 P0；表达层细节（提示文案、界面措辞）无依据为 P2；来源标注写法不规范为 P3。

## 第 6 步：修订（`--no-edit` 时跳过）

按 constitution 第 6 节区分权限：

| 问题所在层 | 处理 |
|---|---|
| 表达层：措辞、结构、编号、格式、引用写法、AC 与已溯源条目的对应 | 直接修改 |
| 决策层：问题定义、范围、设计结论、规则、权限、数字、红线、验收口径 | **不直接决定**。来源不实或缺失的，改标 `提案` 并登记 `Q-n`、给出建议口径，或退回 `[待补充]`（CN-40） |

禁止事项：
- 不得以另一条无来源内容替换被退回的内容。
- 不得为无依据的内容补写 `SRC-n` 或 `CTX`。
- 不得为了通过 lint 而删除有意义的内容。

- 每个新增或改标的 `提案` 都要能对应到一个 `Q-n`：与已有问题相关的，并入该 `Q-n` 并更新其「阻塞什么」；无关的，新建 `Q-n`。
- 修正依赖关系时，可以修改本需求的 `depends_on`，以及对方需求 frontmatter 的 `blocks`（只限该字段）。
- 同步生成报告的模块判定与条目引用，保留原判断和修订原因的摘要。报告缺失时按模块目录补建，仅记录迁移与当前审查事实。`--no-edit` / `--score-only` 不改报告或正文，只输出发现。

修订后再次运行 `prd_lint`，确认没有引入新问题。在需求文件的「修订记录」中追加一行，说明本次审稿修订。「本版变更」与「修订记录」中描述修改时，不要原样引用被修改的非规范写法（如「提案：」），以免被 lint 误报。

## 第 7 步：评分

- 默认模式下，对**修订前的版本**给出门禁判定与质量维度评级（`core/rubric.md` 第 1、2 节），写入 `review-findings.yaml` 的 `rating` 段。审稿器不给自己的修订打分。
- 修订后的评分，由用户或另起的子代理以 `--score-only` 模式完成。
- 每个维度的评级须写明依据（对应的问题编号）。

## 第 8 步：报告

在对话中给出：

1. 问题数量：按 P0–P3 统计，列出全部 P0、P1；其中编造数与素材遗漏数单独列出。
2. 已直接修改的内容（表达层）。
3. **需要人来决策的事项**：新增或改标的 `提案` 与 `Q-n`，附建议口径。这是报告中最重要的部分。
4. 门禁状态：G-1 至 G-5 逐项通过或不通过。
5. 判断：人工需要补的主要是业务事实（说明素材不足）还是表达结构（说明 Skill 需要改进）。
6. 建议的提交信息：`<需求ID>: 审稿修订`。
